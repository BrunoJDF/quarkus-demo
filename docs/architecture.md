## Distribucion de paquetes
- application: Contiene la logica de negocio de la aplicacion, es decir, las reglas de negocio y las operaciones que se pueden realizar sobre los objetos del dominio. Esta capa no debe contener detalles de implementacion, solo las interfaces que definen las operaciones que se pueden realizar sobre los objetos del dominio.
- domain: Contiene los objetos del dominio, es decir, las entidades y los objetos de valor que representan el modelo de negocio de la aplicacion. Esta capa no debe contener detalles de implementacion, solo las clases que representan los objetos del dominio.
- infrastructure: Se funcion como una capa de adaptadores, es decir, se encargara de implementar las interfaces definidas en la capa `application` y de comunicarse con el exterior (base de datos, servicios externos, etc). Esta capa no debe contener logica de negocio, solo la implementacion de las interfaces definidas en la capa `application`.

## Arquitectura hexagonal
La arquitectura hexagonal, también conocida como arquitectura de puertos y adaptadores, es un estilo de arquitectura de software que se enfoca en separar la logica de negocio de los detalles de implementacion. En esta arquitectura, la logica de negocio se encuentra en el centro (el hexagono) y se comunica con el exterior a traves de puertos (interfaces) y adaptadores (implementaciones de las interfaces). Esto permite que la logica de negocio sea independiente de los detalles de implementacion, lo que facilita el mantenimiento y la escalabilidad de la aplicacion. En esta arquitectura, la capa `application` se encuentra en el centro (el hexagono) y se comunica con el exterior a traves de puertos (interfaces) y adaptadores (implementaciones de las interfaces) que se encuentran en la capa `infrastructure`. La capa `domain` se encuentra en el centro del hexagono, ya que representa el modelo de negocio de la aplicacion y es independiente de los detalles de implementacion.

## Patrones de diseño
- Repository: El patron de diseño Repository se utiliza para abstraer el acceso a los datos y proporcionar una interfaz para interactuar con los objetos del dominio. En este patron, se define una interfaz que contiene los metodos para realizar operaciones CRUD (crear, leer, actualizar, eliminar) sobre los objetos del dominio, y luego se implementa esta interfaz en la capa `infrastructure` para interactuar con la base de datos u otros sistemas de almacenamiento. Esto permite que la logica de negocio en la capa `application` no tenga que preocuparse por los detalles de implementacion del acceso a los datos, lo que facilita el mantenimiento y la escalabilidad de la aplicacion. Ademas, el patron Repository permite que se puedan cambiar los detalles de implementacion del acceso a los datos sin afectar la logica de negocio, lo que facilita la adaptacion a cambios en los requisitos o en la tecnologia utilizada para el almacenamiento de datos.
- Service: El patron de diseño Service se utiliza para encapsular la logica de negocio en servicios que pueden ser reutilizados en diferentes partes de la aplicacion. En este patron, se define una interfaz que contiene los metodos para realizar operaciones sobre los objetos del dominio, y luego se implementa esta interfaz en la capa `application` para encapsular la logica de negocio. Esto permite que la logica de negocio sea independiente de los detalles de implementacion, lo que facilita el mantenimiento y la escalabilidad de la aplicacion. Ademas, el patron Service permite que se puedan reutilizar los servicios en diferentes partes de la aplicacion, lo que facilita la adaptacion a cambios en los requisitos o en la tecnologia utilizada para la implementacion de la logica de negocio.
- Adapter: El patron de diseño Adapter se utiliza para adaptar una interfaz a otra, lo que permite que dos sistemas incompatibles puedan trabajar juntos. En este patron, se define una clase que implementa la interfaz que se desea adaptar y que contiene una instancia de la clase que se desea adaptar. Luego, se implementan los metodos de la interfaz adaptada para llamar a los metodos de la clase adaptada. Esto permite que la logica de negocio en la capa `application` no tenga que preocuparse por los detalles de implementacion del acceso a los datos o de otros sistemas externos, lo que facilita el mantenimiento y la escalabilidad de la aplicacion. Ademas, el patron Adapter permite que se puedan cambiar los detalles de implementacion del acceso a los datos o de otros sistemas externos sin afectar la logica de negocio, lo que facilita la adaptacion a cambios en los requisitos o en la tecnologia utilizada para el almacenamiento de datos o para la comunicacion con otros sistemas externos.
- Input: El patron de diseño Input se utiliza para encapsular una solicitud como un objeto, lo que permite que se puedan parametrizar los clientes con diferentes solicitudes, encolar o registrar las solicitudes, y soportar operaciones de deshacer. En este patron, se define una interfaz que contiene un metodo para ejecutar la solicitud, y luego se implementa esta interfaz en la capa `application` para encapsular la logica de negocio. Esto permite que la logica de negocio sea independiente de los detalles de implementacion, lo que facilita el mantenimiento y la escalabilidad de la aplicacion. Ademas, el patron Input permite que se puedan parametrizar los clientes con diferentes solicitudes, encolar o registrar las solicitudes, y soportar operaciones de deshacer sin afectar la logica de negocio, lo que facilita la adaptacion a cambios en los requisitos o en la tecnologia utilizada para la implementacion de la logica de negocio.
- DTO: El patron de diseño DTO (Data Transfer Object) se utiliza para transferir datos entre diferentes capas de la aplicacion, lo que permite que se puedan separar las preocupaciones de cada capa y evitar la dependencia entre ellas. En este patron, se define una clase que contiene los atributos necesarios para transferir los datos entre las capas, y luego se utiliza esta clase para transferir los datos entre las capas. Esto permite que la logica de negocio en la capa `application` no tenga que preocuparse por los detalles de implementacion del acceso a los datos o de otros sistemas externos, lo que facilita el mantenimiento y la escalabilidad de la aplicacion. Ademas, el patron DTO permite que se puedan cambiar los detalles de implementacion del acceso a los datos o de otros sistemas externos sin afectar la logica de negocio, lo que facilita la adaptacion a cambios en los requisitos o en la tecnologia utilizada para el almacenamiento de datos o para la comunicacion con otros sistemas externos.
- Factory: El patron de diseño Factory se utiliza para encapsular la creacion de objetos, lo que permite que se puedan separar las preocupaciones de cada capa y evitar la dependencia entre ellas. En este patron, se define una interfaz que contiene un metodo para crear el objeto, y luego se implementa esta interfaz en la capa `application` para encapsular la logica de negocio. Esto permite que la logica de negocio sea independiente de los detalles de implementacion, lo que facilita el mantenimiento y la escalabilidad de la aplicacion. Ademas, el patron Factory permite que se puedan cambiar los detalles de implementacion de la creacion de objetos sin afectar la logica de negocio, lo que facilita la adaptacion a cambios en los requisitos o en la tecnologia utilizada para la implementacion de la logica de negocio.
- Builder: El patron de diseño Builder se utiliza para construir objetos complejos paso a paso, lo que permite que se puedan separar las preocupaciones de cada capa y evitar la dependencia entre ellas. En este patron, se define una clase Builder que contiene los atributos necesarios para construir el objeto, y luego se utiliza esta clase para construir el objeto paso a paso. Esto permite que la logica de negocio en la capa `application` no tenga que preocuparse por los detalles de implementacion de la creacion de objetos complejos, lo que facilita el mantenimiento y la escalabilidad de la aplicacion. Ademas, el patron Builder permite que se puedan cambiar los detalles de implementacion de la creacion de objetos complejos sin afectar la logica de negocio, lo que facilita la adaptacion a cambios en los requisitos o en la tecnologia utilizada para la implementacion de la logica de negocio.
- Singleton: El patron de diseño Singleton se utiliza para garantizar que una clase tenga una unica instancia y proporcionar un punto de acceso global a esa instancia. En este patron, se define una clase que contiene un atributo estatico que almacena la unica instancia de la clase, y luego se proporciona un metodo estatico para acceder a esa instancia. Esto permite que se pueda garantizar que solo exista una unica instancia de la clase, lo que puede ser util en situaciones donde se necesita un punto de acceso global a un recurso compartido, como una conexion a una base de datos o un servicio externo. Ademas, el patron Singleton permite que se puedan cambiar los detalles de implementacion de la clase sin afectar el punto de acceso global, lo que facilita la adaptacion a cambios en los requisitos o en la tecnologia utilizada para la implementacion de la logica de negocio.
